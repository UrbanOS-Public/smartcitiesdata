Forklift & Trino: Nested Timestamp Caveats

Why mdot__prune_test_2 never migrated from its __json staging table into the queryable main table — and why the same "timestamp" schema type works fine elsewhere. Found while troubleshooting dataset_id = e4afd220-6842-434b-bf55-b4f4ed01043b, ingestion_id = d336978f-2285-43dc-8e7b-f106e6b3b681, week of 2026-07-16.

This page documents two independent timestamp-handling bugs found on this same dataset in separate investigations — a nested-column parsing failure (Problem 1, below) and a 32-bit integer overflow on an unrelated field (Problem 2, found 2026-08-07) — plus a production-wide audit (2026-08-11) for datasets exposed to the same class of risk as Problem 2.

Why this exists

A dev dataset (mdot__prune_test_2, an MDOT ESS/RWIS environmental sensor feed) looked broken end to end: querying it via discovery-api returned nothing useful. The underlying cause turned out to be a one-line serialization bug that only bites when a "timestamp"-typed schema field is nested inside a repeated struct (array(row(...))) rather than sitting at the top level of the record — and it fails silently, with no retry and no alert, until the data is quietly deleted by a retention job a week later. This document is the condensed trail so the next person who hits HIVE_CURSOR_ERROR on a migration doesn't have to re-walk all of it.

The symptom

Every single extraction cycle for this dataset (~every 5 minutes, 100% of attempts, across multiple days) failed identically in Forklift's DataMigration.compact/3: 

[error] Error migrating records for dataset e4afd220-6842-434b-bf55-b4f4ed01043b: mdot__prune_test_2,
ingestion: d336978f-2285-43dc-8e7b-f106e6b3b681, extract: 1784745001
%Prestige.Error{
  code: 16777217,
  name: "HIVE_CURSOR_ERROR",
  type: "EXTERNAL",
  message: "Failed to read file at s3a://presto-hive-storage/hive-s3/mdot__prune_test_2__json/
            _extraction_start_time=1784745001/_ingestion_id=d336978f-.../1784745144--....gz"
}

Reproduced live via an interactive PrestigeHelper.execute_query/1 call days later, byte-for-byte identical — confirming this is deterministic, not a transient blip.

What we ruled out first

HIVE_CURSOR_ERROR is a generic wrapper Trino uses for almost any failure while reading a file's contents, so the investigation spent most of its time eliminating plausible causes before landing on the real one.

The actual root cause

show create table mdot__prune_test_2__json declares status.sensorstatus[].datetime as timestamp(3). But the value Forklift actually writes into the JSON file is a space-separated string with no fractional seconds at all: 

"dateTime": "2026-07-20 15:22:00"

That's produced deliberately — not a stray formatting accident — by apps/pipeline/lib/pipeline/writer/s3_writer/s3_safe_json.ex:28-30: 

defp format_data(value, %{type: "timestamp"}) do
  Timex.parse!(value, "{ISO:Extended}") |> Timex.format!("{ISOdate} {h24}:{m}:{s}")
end

The source value arrives as proper ISO-8601 (parsing requires that), and this function deliberately re-emits it without a T separator and without milliseconds. That's consistent with a real product requirement — the Michigan implementation is understood to have asked for sub-second precision to be dropped — not a bug in intent. The problem is that this reformatted value then gets read back by Trino's Hive JSON connector into a declared timestamp(3) column, and for this specific nested usage, that parse fails on every single row.

The reformat step is identical for every dataset using type: "timestamp". The failure only shows up for this dataset's specific column shape — see below.

Why one dataset works and the other doesn't

s3_safe_json.ex is shared code — every dataset with a "timestamp" field goes through the exact same reformatting. If the reformatted string itself were universally unparsable by Trino, every dataset using this type would be broken. It isn't. Directly comparing the two tables' DDL:

mdot__gist_truck_parking_static__json (works)mdot__prune_test_2__json (broken)
Column shape timestamp timestamp(3) — top-level scalar status.sensorstatus[].datetime timestamp(3) — three levels deep, inside array(row(...))
Migrates successfully today? yes zero errors in the log, same ~5 min cadence no 100% failure rate, every cycle
Goes through S3SafeJson.format_data/2? Yes, identical code path Yes, identical code path

Since the write-side transform is identical either way, the most likely explanation is that Trino's Hive JSON connector applies timestamp parsing differently (or less leniently) for a field nested inside a repeated struct than for a plain top-level column. This has not been isolated with a controlled test (e.g. a minimal reproduction table with just a nested timestamp column) — see caveats.

Implication: s3_safe_json.ex does not need to change. It's working correctly for the shape of data it was presumably designed and tested against (top-level timestamps), and touching shared serialization code to fix one nested-field edge case risks regressing every dataset that currently works fine. The fix belongs in this one dataset's schema, not in shared platform code.

A separate, serious finding: silent permanent data loss

Independent of root cause, tracing what happens after a migration failure turned up a second, more general problem worth fixing regardless of this specific dataset:

No retry, then a 7-day silent purge

Forklift.Jobs.DataMigration.compact/3 has no retry on failure — it logs the error, marks status :error, and never revisits that specific (ingestion_id, extraction_start_time) again (apps/forklift/lib/forklift/jobs/data_migration.ex:65-75). Meanwhile, Forklift.Jobs.PartitionedCompaction.remove_stale_data_from_json_table/1 runs daily and unconditionally deletes any __json row older than 7 days, purely by age (apps/forklift/lib/forklift/jobs/partitioned_compaction.ex:91-96) — with no check for whether that data was ever successfully migrated.

Net effect: any migration failure, whatever the cause, is not a delay — it's a countdown. After 7 days the never-migrated data is deleted from staging with no distinct log line and no alert distinguishing it from routine cleanup of already-migrated rows.

The fix we're applying

Scoped to this one dataset, lowest blast radius:

  1. In ANDI's Data Dictionary editor, change dateTime's field type from timestamp to string. This routes the value through S3SafeJson's catch-all clause (s3_safe_json.ex:59-61) instead of the timestamp branch — no parsing, no reformatting, written through byte-for-byte.
  2. Drop the existing mdot__prune_test_2__json and mdot__prune_test_2 tables. Forklift's dataset_update handler only creates tables with CREATE TABLE IF NOT EXISTS (apps/forklift/lib/forklift/event/event_handler.ex:75-104) — it has no ALTER-TABLE path, so an existing table's column type will not change just by republishing.
  3. Click Publish in ANDI after the drop, so the resulting dataset_update event finds the tables missing and recreates them with the corrected schema.

This is destructive to whatever data currently sits in both tables (the small amount that ever migrated, plus whatever's stuck in staging) — acceptable for a test dataset, and each DROP TABLE was run deliberately by hand rather than automated.

Caveats & open questions

  • The nesting-depth theory is a strong structural inference, not a proven mechanism. We compared two real tables and found a clean correlation (nested fails, top-level works), but never isolated it with a minimal repro table containing only a nested timestamp column. If Trino's actual behavior turns out to be something else nesting-adjacent (e.g. array-vs-row handling generally, not timestamps specifically), this document's explanation would need revising.
  • The dropped-sub-second-precision behavior in s3_safe_json.ex is believed intentional (Michigan implementation request), based on context from the engineer investigating, not a code comment or design doc found in-repo. Worth confirming with whoever owns that requirement before anyone is tempted to "fix" the format string globally.
  • The no-retry / 7-day-purge risk is not specific to timestamps at all. Any dataset that hits any persistent migration failure — this bug, a future one, or an entirely unrelated cause — will silently and permanently lose the affected data on the same 7-day clock. That's a standing platform gap independent of this fix, not addressed by changing this one dataset's schema.
  • Getting the real Trino-side nested exception proved to be a dead end via logs. Both the coordinator's QueryMonitor summary line and a live interactive reproduction returned identical, terse HIVE_CURSOR_ERROR structs with no deeper cause chain. If this class of failure recurs, DEBUG-level logging for io.trino.plugin.hive (config change + restart) is the only path found so far to a genuine nested IOException/parse-error message.
  • Resolution not yet verified end-to-end. The schema edit / table drop / republish sequence above was planned and about to be executed at the time this document was written; confirm the next few extraction cycles actually migrate cleanly before considering this closed.

Problem 2: int32 overflow on modified.date

A second, unrelated bug on the same dataset (mdot__prune_test_2), found in a later investigation on 2026-08-07. It shares the generic HIVE_CURSOR_ERROR symptom with Problem 1 above, and both are legitimately "timestamp-like field mishandled by Hive/Trino" — but the mechanism, the field, and the fix are entirely different. This is not a continuation or correction of Problem 1; treat them as two separate defects that happened to land on the same dataset.

Problem 1 (above)Problem 2 (this section)
Fieldstatus.sensorstatus[].datetimemodified.date
Declared typetimestamp(3)integer
MechanismNested (array(row(...))) timestamp column can't parse the no-milliseconds string format Forklift writes for top-level timestamps Hive 32-bit integer column overflows on a 13-digit millisecond-epoch value
FoundWeek of 2026-07-162026-08-07

Root cause

data_dictionary row dcd2178c-6950-4a0f-a477-44239ff9c9cc (modified > date, ingestion d336978f-2285-43dc-8e7b-f106e6b3b681, "ATMSQA ESS 4.0") is typed integer — a Hive 32-bit int, max ±2.147 billion. The real source values are millisecond-epoch timestamps: 

"modified": {"date": 1777987738000, "user": "NguyenD5"}

1,777,987,738,000 overflows a 32-bit int on every single record. The working sibling dataset mdot__ess_test (74f4bcfa-2f53-4136-a5be-d9b987ea42f6, same ingestion) declares the identical field float instead, and reads fine.

Precision check: traced schema type "float" through apps/pipeline/lib/pipeline/writer/table_writer/statement/create.ex (the @field_type_map that drives CREATE TABLE DDL, lines 6–16) — it maps to Trino/Hive double (64-bit), not single-precision real. A double exactly represents integers up to 253 (≈9 quadrillion), so retyping date as float is precision-safe for this 13-digit value, not merely overflow-safe. "long" (→ bigint) would be the more semantically honest type for an epoch integer, but isn't required for correctness here.

The fix

update data_dictionary set type = 'float' where id = 'dcd2178c-6950-4a0f-a477-44239ff9c9cc';

Followed by the same drop/republish mechanics as Problem 1 above (Forklift's dataset_update handler is CREATE TABLE IF NOT EXISTS only, so an existing table's column type won't change just by republishing): drop mdot__prune_test_2__json and mdot__prune_test_2, then publish in ANDI to recreate both with the corrected schema.

Status: as of 2026-08-07 this fix had been diagnosed and identified against a local restored DB snapshot, but had not yet been applied to the live cluster. Verify current status before assuming this is resolved.

Production audit: who else is exposed

2026-08-11: queried the two restored production Postgres snapshots (andi_prod_20260227, andi_prod_20260729) to check whether the Problem 2 overflow class exists anywhere else. mdot__prune_test_2 and mdot__ess_test are QA/dev-org (mdot) datasets and aren't present in either production snapshot, so this audit covers the real production michigan_department_of_transportation org (12 datasets, 8 ingestions in the most recent snapshot).

Finding: no production dataset currently has the Problem 2 bug — but four production ingestions share the exact same overflow-prone field shape, and are one schema edit away from reproducing it on real data.
IngestionTarget dataset(s) (systemName)
ATMS DMSdynamic_message_signs, dms_message
ATMS Parkingtruck_parking_dynamic, atms_parking
ATMS Parking TPIMS Statictruck_parking_static
ATMS Prod Eventsatms_events_for_cv

Each declares a modified (and, for ATMS Prod Events, also created) field as opaque type: "map" in data_dictionary, with no expanded sub-fields. Because the map is never expanded, Hive never attempts to cast the nested date value as a 32-bit int, so the overflow never triggers today. This is accidental protection, not a deliberate fix: prune_test_2's QA ingestion ("ATMSQA ESS 4.0") hit the bug specifically because someone expanded that same modified map into typed sub-fields via ANDI and typed date as integer. The raw source shape ("modified": {"date": <epoch-ms>, "user": "..."}) is confirmed shared across this whole MDOT ATMS API family, so expanding modified/created on any of the four ingestions above and typing the nested date field integer would reproduce this exact crash on production data.

No standard convention for date/time fields in production

Neither prod snapshot uses the schema system's own "timestamp", "date", or "long" types at all. The only data_dictionary types in active production use are boolean, float, integer, json, list, map, string. Date/time values are represented three different, uncoordinated ways:

ConventionWhere
Opaque map, never expandedATMS family (all four ingestions above)
Free-text string, ISO datetimeXML Incident From Mi Drive: actdatetime, enddatetime, startdatetime
float (Trino double)Dynamic Message Sign Status.timestamp — the only expanded numeric timestamp field found in prod
Recommendation, not yet acted on: if modified/created is ever expanded on any of the four ATMS ingestions above, the nested epoch sub-field must be typed float or long — never integer. Worth considering as a standing rule for this API family, and as a candidate for a schema-validation lint in ANDI (flag integer type when a field's sample value exceeds ≈2.1 billion) rather than relying on nobody expanding these maps.
