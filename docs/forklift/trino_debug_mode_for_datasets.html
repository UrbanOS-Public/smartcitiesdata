Enabling Trino Hive-Connector DEBUG Logging

Why this is necessary

HIVE_CURSOR_ERROR is Trino's generic wrapper for "something went wrong while reading this file's contents" — it is deliberately uninformative on its own. Every attempt to get more detail from the client side of the connection came back with the exact same terse struct, whether captured from the application log (Logger.error(inspect(error))) or reproduced live via an interactive Prestige query: 

%Prestige.Error{
  code: 16777217,
  name: "HIVE_CURSOR_ERROR",
  type: "EXTERNAL",
  message: "Failed to read file at s3a://presto-hive-storage/hive-s3/..."
}

That is all the Trino client/server protocol carries back for this error class — not a limitation of how it was captured. Meanwhile, direct inspection of the failing files themselves (gzip integrity, JSON parse, per-field type consistency, schema-shape diff against the live DDL) came back clean on every check across three separately-pulled files. There is nothing further to learn by looking at the file from the outside. The only remaining place the real cause can be seen is the nested exception Trino's Hive connector catches and discards before re-throwing the generic wrapper — which only appears in the connector's own internal logging, normally suppressed below INFO level.

What's being swallowed today

The real cause is thrown and caught entirely inside the Hive connector, on whichever worker executes the split. At INFO level (Trino's default) that detail never leaves the connector. Raising the connector's own log level to DEBUG is what makes it visible.

Locating the logging config

Trino (built on Airlift) reads its logger levels from etc/log.properties at process start. The setting needed is: 

io.trino.plugin.hive=DEBUG
Check this before editing anything: whether log.properties is baked into the pod's image or mounted from a ConfigMap determines whether an in-place edit survives a restart. 
kubectl describe pod <trino-coordinator-pod> -n mdot-ride-<env>-ns
kubectl describe pod <trino-worker-pod>      -n mdot-ride-<env>-ns
Look under Volumes/Mounts for anything referencing log.properties or a Trino config ConfigMap.
  • ConfigMap-mounted: edit the ConfigMap itself (kubectl edit configmap <name> -n <ns>), then restart the pod(s) so they remount the updated file. An in-place kubectl exec edit would be silently discarded on the next restart.
  • Baked into the image: an in-place edit via kubectl exec is the only option short of a Helm values change; it will not survive a pod restart, so the DEBUG window only lasts until something else causes the pod to cycle.

The procedure

  1. Edit the config on both the coordinator and the worker. This dataset's split read happens on a worker, but enabling on both avoids guessing which node handles it if the cluster ever has more than one worker. 
    kubectl exec -it <trino-worker-pod> -n mdot-ride-<env>-ns -- sh -c \
  'echo "io.trino.plugin.hive=DEBUG" >> /etc/trino/log.properties'
    (Adjust the path if kubectl describe pod showed a different mount point.)
  2. Restart the process so the new level takes effect. Trino reads log.properties at bootstrap only — there is no live-reload for this file. If the config is ConfigMap-backed, make the ConfigMap edit first, then: 
    kubectl delete pod <trino-worker-pod> -n mdot-ride-<env>-ns
kubectl delete pod <trino-coordinator-pod> -n mdot-ride-<env>-ns
    Wait for both to report Running again before proceeding.
  3. Start tailing the worker's log before triggering the failure, so nothing is missed: 
    kubectl logs -f <trino-worker-pod> -n mdot-ride-<env>-ns > worker_debug.log &
  4. Reproduce the failure — see below for the exact one-liner rather than waiting for the next 5-minute extraction cycle.
  5. Stop the tail and search the capture for the query ID or the file path from the resulting Prestige.Error — see Reading the DEBUG output.
  6. Revert the logging level once the nested exception has been captured.

Reproducing on demand

No need to wait for the next scheduled extraction cycle. The failing data is already sitting in the __json staging table (that's the whole problem — it never migrates out), so the exact same read Forklift's DataMigration.compact/3 performs can be run directly from a live Forklift console, the same way it was used throughout this investigation: 

kubectl exec -it <forklift-pod> -n mdot-ride-<env>-ns -- bin/forklift remote
iex> Pipeline.Writer.TableWriter.Helper.PrestigeHelper.execute_query(
...>   "select * from mdot__prune_test_2__json " <>
...>   "where _ingestion_id = 'd336978f-2285-43dc-8e7b-f106e6b3b681' " <>
...>   "and _extraction_start_time = 1785110401"
...> )

Swap in the ingestion id / extraction time from whichever fresh Error migrating records for dataset ... line is most recent (or from scripts/diagnose_ingestion.py's forklift_migration_error category output). This is read-only — no insert/delete side effects, unlike the real migration statement — and it hits the identical file, so it reproduces the identical failure on demand.

Reading the DEBUG output

Expect a lot more volume. io.trino.plugin.hive=DEBUG is chatty across every query the cluster runs, not just the one being reproduced. Don't try to read the tail as a stream — capture to a file and search it after triggering the reproduction query.

Once the query above has been run, search the capture for the exact file path from its result:

grep -A 40 "1785110435--576460752242861759.gz" worker_debug.log

Look for the first Caused by: line in that block — that's the actual underlying exception (a JSON type-coercion failure, a truncated-read/EOF, a splittability complaint about the non-splittable gzip format, or something not yet guessed at) that HIVE_CURSOR_ERROR has been hiding since day one of this investigation.

What the Caused by: line namesWhat it would mean
A JSON/Jackson parse or type-coercion exception, naming a specific column A field still doesn't match its declared column type — back to schema/DDL inspection, but now pointed at the exact field instead of guessing.
EOFException / unexpected end of stream The file is being truncated mid-read despite passing gzip -t standalone — points at a streaming/range-read problem on Trino's side, not the file's own integrity.
Something about split boundaries / non-splittable compression Points at how Trino is chunking reads of a large non-splittable gzip file, independent of this dataset's content entirely.
An S3/MinIO connection-level exception (timeout, reset, precondition failed) Storage-layer, not data-layer — revives the read-after-write consistency theory from earlier in this investigation, now with real evidence instead of speculation.

Reverting

Remove the io.trino.plugin.hive=DEBUG line (from the ConfigMap if that's where it was added) and restart both pods again. Hive-connector DEBUG logging is verbose enough that leaving it on materially inflates log volume across every dataset the cluster serves, not just this one — it should not be left enabled once the nested exception has been captured.

Caveats

  • Exact config paths are unverified for this cluster. /etc/trino/log.properties is the conventional location for the official Trino Docker image, but this repo has no Helm chart or manifest for the Trino deployment itself to confirm it — kubectl describe pod first, as in Locating the logging config, rather than assuming the path below is correct.
  • This assumes the failure reproduces deterministically, which every capture so far supports (100% failure rate, same file, same error, across multiple days) — but if the underlying cause ever turns out to be a race or timing-dependent, a single reproduction attempt while DEBUG is on might not trigger it.
  • Restarting the worker does not fix the bug, confirmed earlier in this investigation (identical HIVE_CURSOR_ERROR reproduced on a brand-new worker pod at the same cadence). Restarting here is purely to load the new log level, not an attempted fix.
  • This is a diagnostic step, not a resolution. Whatever the nested exception says still needs to be traced back to a concrete fix (a schema field, a Trino/connector setting, or a storage-layer issue) once it's known.
