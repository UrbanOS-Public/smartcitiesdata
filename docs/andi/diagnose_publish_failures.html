Why this exists

ANDI's Publish button can fail with no useful information in the UI. The banner it shows on failure is hard-coded to the same soft message regardless of what went wrong, and the error ANDI itself logs server-side is frequently [] — an empty list — even when the underlying data is genuinely invalid. That's not a fluke; it's how Ecto.Changeset.errors works: it only holds errors attached directly to the top-level changeset, never the ones nested inside cast_assoc children (schema fields, extract steps, transformations). Reproducing the failure and calling Ecto.Changeset.traverse_errors/2 instead is the only way to see what's actually wrong.

Andi.Scripts.PublishDiagnostics (apps/andi/lib/andi/scripts/publish_diagnostics.ex) wraps that up into single function calls, plus two checks for the specific failure modes this week's incident turned up.

How publish validation actually works

The single biggest source of confusion this week: saving a draft validates almost nothing, and the Publish button's own error log is misleading. The diagram below traces both save paths side by side.

Draft-save (left, green) never validates ingestion_field_selector or most other required fields — that's why bad data can sit for days unnoticed. Publish (right) runs the strict validator, but its own top-level changeset.errors (bottom right, red) is usually empty when the real problem is nested. diagnose_ingestion/1 runs the same strict path and prints the nested errors instead.

Function reference

diagnose_ingestion(ingestion_id) start here

Runs the exact validation the Publish button runs (Ingestion.changeset(%{}) |> Ingestion.validate()), then uses Ecto.Changeset.traverse_errors/2 to print every nested error instead of the misleading flat list. Also runs check_top_level_selector/1 and find_blank_ingestion_field_selectors/1 automatically and folds their output in.

  valid?: false
  Nested validation errors:
  errors: %{schema: [%{ingestion_field_selector: ["is required"]}, ...]}
  topLevelSelector: nil/empty -- whole payload will be treated as one record. OK.
  17 schema field(s) missing ingestion_field_selector:
    - features (id=...)
    - road_event_feed_info (id=...)

    ...

diagnose_dataset(dataset_id)

Same idea, against the Dataset's own publish path (Dataset.changeset/2 |> validate_unique_system_name/1). Use this for datasets that aren't sourceType: "ingest", or to sanity-check a target dataset independently of its ingestion.

check_top_level_selector(ingestion_id)

Flags a topLevelSelector that's syntactically valid JSONPath but semantically a no-op — e.g. the literal two characters "" instead of a truly empty/nil value. Jaxon.Path.parse/1 accepts it silently; Reaper.Decoder.Json then matches zero keys against it, so extraction returns 0 records every cycle with no error anywhere in the pipeline — just an END_OF_DATA sentinel on repeat. This was bug #1 in the f4822954 incident.

find_blank_ingestion_field_selectors(ingestion_id)

Recursively walks the schema tree (including nested subSchema) and lists every field whose ingestion_field_selector is nil or "". This value is required to publish, but ANDI's Ingestion schema editor currently has no UI control that can ever set it — see the gap diagram below. This was bug #2 in the f4822954 incident.

fix_blank_ingestion_field_selectors(ingestion_id, dry_run: false) mutates data

Sets every blank ingestion_field_selector to that field's own name — the same thing the Dataset editor's "Sync Ingestion Field" checkbox would have done, had that control been reachable for ingestion-scoped schemas. Defaults to a dry run (prints what it would change); pass dry_run: false to persist.

This is only semantically correct when the payload's JSON keys match your schema field names 1:1 (true for the WZDX case, and for most flat mappings). It is not a universal fix — ingestion_field_selector is the real extraction key Valkyrie uses to pull each field's value out of the incoming record (apps/valkyrie/lib/valkyrie.ex:30-32), so double check it matches your actual source payload before trusting it blindly.

check_wire_schema(ingestion_id) / check_wire_schema_for_dataset(dataset_id)

Prints three numbers side by side instead of just flagging the question below:

  1. Postgres, unstripped (Ingestions.get/1) — the actual source of truth Ingestion.validate/1 checks at publish time.
  2. would-publish-now (andi_ingestion_to_smrt_ingestion/1) — what today's conversion code would put on the wire if republished right now. This line will read MISSING for every ingestion, always, because drop_fields_from_dictionary_item/1 deletes the key unconditionally — it doesn't check whether Postgres was good first. Don't read this line in isolation; it's printed to make the stripping visible, not to judge data health.
  3. live Brook view (IngestionStore.get/1) — ANDI's own view of the last event that was actually published and consumed. This is what Reaper / Alchemist / Valkyrie / Forklift are running on right now.

The comparison that actually matters is line 1 vs. line 3 — Postgres today vs. the live artifact:

iex> Andi.Scripts.PublishDiagnostics.check_wire_schema("f4822954-1c0d-482e-9208-f45f5620c5a2")
Ingestion f4822954-1c0d-482e-9208-f45f5620c5a2
  Postgres, unstripped (Ingestions.get/1): ingestion_field_selector MISSING/blank on 17/17 field(s)
  would-publish-now (andi_ingestion_to_smrt_ingestion/1): ingestion_field_selector MISSING/blank on 17/17 field(s)
  live Brook view (IngestionStore.get/1): nothing published yet
  • Postgres present, live view present — healthy. Republishing would succeed (modulo other validation) and, once the "is required" gate is removed, would keep working via Valkyrie's name-default fallback exactly as it does today.
  • Postgres MISSING, live view present — the pipeline is only working because it's still running on an old event published before Postgres went blank (or before ingestion_field_selector existed at all). Nothing is broken today, but Publish will fail right now for this record, with no error visible in the UI, for exactly the reason this whole document exists. This is the case a Redis flush gets blamed for — it isn't the cause, but recovery work after one is often what first forces someone to re-open and re-save a record that hasn't been touched in years.
  • Postgres MISSING, live view also MISSING/never published — a fresh record that has never made it through Publish, or one published after the required-field gate was already removed.

The "Ingestion Field" UI gap

ingestion_field_selector is required to publish an ingestion, but tracing every path a schema field can take through ANDI shows the Ingestion editor has no way to ever set it. The Dataset editor and the JSON API both work; the Ingestion editor's own UI does not.

Same required field, three different paths. Only the middle column — ANDI's own Ingestion editor — can never produce a valid value through the UI. This is why a production user publishing via script/API, or via the Dataset editor, never sees this; you were the first to build this ingestion's schema by hand in the Ingestion editor.

Confirmed: both publish-time conversions (InputConverter.andi_ingestion_to_smrt_ingestion/1 and convert_andi_technical/1) strip ingestion_field_selector out of the schema entirely before it's ever put on the wire as a SmartCity.Ingestion / SmartCity.Dataset event — the "would-publish-now" line of check_wire_schema/1 reads MISSING for 100% of every production ingestion tested, with no exceptions, which is exactly what unconditional stripping predicts.

What's still per-record, not yet a blanket fact: running the original two-line version of check_wire_schema/1 against seven production ingestions (all 12–36 fields each, all published over roughly the last two years) showed every one of them with a complete, correct ingestion_field_selector in the live Brook view — meaning the running pipeline for all seven is fine. That result alone doesn't say whether Postgres is also still fine for those same seven (the old two-line version couldn't distinguish that, which is why the three-line version above exists now). Run find_blank_ingestion_field_selectors/1 or the updated check_wire_schema/1 against a record before editing/republishing it — if Postgres line comes back blank, Publish will fail today with the same silent changeset.errors: [] symptom as the original incident, regardless of how long the record has been published and working.

Case study walkthrough

Applying the tools above to f4822954-1c0d-482e-9208-f45f5620c5a2 end to end:

  1. Pipeline logs showed extraction running clean every 5 minutes, but Forklift aborting migration every cycle: reason No data found to migrate.
  2. Pulling the raw Kafka messages off validated-c852c698-... showed every single one was {"payload":"END_OF_DATA", ...} — no real record ever made it that far.
  3. check_top_level_selector/1 would have caught this immediately: the ingestion's topLevelSelector was the literal string "", a syntactically valid but semantically empty JSONPath, so Reaper.Decoder.Json matched zero records every cycle. Fixed by clearing the field to a genuinely empty value.
  4. Attempting to republish then failed with Ingestion Publish Error: Changeset validation found errors in ingestion: [] in the ANDI logs — the misleading empty-list symptom described above.
  5. diagnose_ingestion/1 (or manually, Ecto.Changeset.traverse_errors/2) surfaced the real problem: all 17 schema fields were missing ingestion_field_selector.
  6. find_blank_ingestion_field_selectors/1 confirmed the exact list and count; fix_blank_ingestion_field_selectors/1 (dry run) confirmed the planned fix before running it with dry_run: false.

Caveats & open questions

  • Flat changeset.errors is not trustworthy. Always read nested errors via traverse_errors/2 (which diagnose_ingestion/1 and diagnose_dataset/1 do for you) — the flat list is frequently [] even when the changeset is invalid, because cast_assoc errors live on child changesets.
  • check_top_level_selector/1 is a heuristic, not a full simulation of extraction. It flags values that are entirely quote characters (~r/^"+$/); it does not run the selector against real sample data.
  • fix_blank_ingestion_field_selectors/2 assumes name == payload key. Verify against a real sample payload before running with dry_run: false on an ingestion whose schema field names don't match the source JSON/XML keys.
  • check_wire_schema/1 tells you what's true right now, not what's always been true. A record that currently shows Postgres and the live Brook view agreeing could still have been republished recently for unrelated reasons, which would reset the live view to match Postgres's current (possibly already-blank) state. A single check is a snapshot, not a guarantee of what the field looked like historically.
  • None of this is caused by a Redis flush, even though recovering from one is often what surfaces it. The required-field list is a hardcoded module attribute (@required_fields in data_dictionary.ex), not read from Redis or any runtime config — a flush can't change what gets validated. What a Redis flush does do is wipe Brook's view-state cache, which then gets silently rebuilt by replaying ANDI's own Kafka event history; the reconstructed view looks identical to before the flush because nothing about the underlying data changed. The real trigger is usually that someone opens and re-saves a record for the first time in years as part of that recovery work, and that's the first time it hits today's stricter validator.
