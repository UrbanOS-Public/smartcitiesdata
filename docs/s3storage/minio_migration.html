MinIO → Self-Hosted S3 Migration Plan

A plan for moving smartcitiesdata (UrbanOS / RIDE) off the in-cluster MinIO Operator tenant and onto a self-hosted, S3-API-compatible object store running outside the OpenShift cluster — covering both consumers of the object store found in this repository: the Elixir applications (ExAws/ExAws.S3) and Trino's native Hive-connector S3 filesystem.

Status: Draft Author: Rob Seward Date: 2026-09-14 Branch: 2026-otp23 Scope: app repo + openshift-deploy repo
Scope note

This repository (smartcitiesdata) only owns application-level object-storage configuration. The actual MinIO/Kubernetes deployment manifests (the minio_tenant_chart Helm chart, MinIO Operator subscription, PVCs, and Trino/Hive Helm values) live in the separate UrbanOS-Public/openshift-deploy repository. This plan is written from the smartcitiesdata side but calls out every place work is also required in openshift-deploy.

1. Why now

Forcing issue

MinIO is currently deployed via the MinIO Operator through OpenShift's OperatorHub marketplace. That distribution path is being removed starting with OpenShift 4.16+, and MinIO's own post-AGPLv3-relicensing options are either the paid AIStor product or a community-maintained, self-managed Operator/Helm deployment with no vendor support path on OpenShift going forward.

Secondary drivers

  • Moving the store outside the cluster removes a large, stateful workload (PVC-backed MinIO tenant pods) from OpenShift capacity planning and upgrade risk — the same class of risk that already caused a cluster-upgrade-triggered crash loop for other in-cluster stateful/operator-managed components on 2026-08-31.
  • Decouples object-storage availability from OpenShift cluster maintenance windows (node drains, operator upgrades) — today, an in-cluster MinIO outage takes down ingestion (Forklift writes), Trino/Hive query serving, and hosted-file upload/download simultaneously.
  • Opens the door to a storage engine chosen for operational fit (e.g. erasure-coded replication, easier off-cluster backup/DR) rather than "whatever OperatorHub still offers."

2. Current architecture

The critical fact driving this whole plan: there are two independent S3 clients talking to the same MinIO tenant today, configured completely separately, and both must be repointed. Missing either one produces a partial, confusing migration (e.g. ingestion writes succeed against the new engine but Trino still reads the old one).

Two independent S3 clients (blue = Elixir ExAws, purple = Trino's native Hive S3 filesystem) both point at one in-cluster MinIO tenant. A browser also talks to MinIO directly via presigned URLs, bypassing Andi entirely for the actual byte transfer.

No app in this repo uses a MinIO-proprietary client or API — every access path goes through the generic ExAws/ExAws.S3 library (Elixir side) or Trino's generic native-S3 Hive filesystem (query side), both pointed at MinIO purely via endpoint/host override. This is good news: any S3-compatible engine that supports path-style addressing, SigV4 request signing/presigned URLs, multipart upload, and ListObjectsV2 should be a drop-in replacement at the protocol level.

6. Pre-migration baseline & synthetic benchmarking

The risk register (Section 12) names network-path latency/throughput to an out-of-cluster store as the single highest-impact risk to this migration, and Phase 5's per-environment exit criteria already require "Trino query latency within an agreed tolerance of the pre-migration baseline." Neither of those is checkable unless a real baseline exists. This section defines what to capture before any endpoint is touched, and a synthetic benchmark tool for generating apples-to-apples numbers against both the current in-cluster MinIO tenant and the candidate replacement engine.

6.1 What to baseline, and where it comes from

Both numbers are needed to separate "this engine is inherently faster/slower" from "this environment changed."

6.2 Trino query performance monitoring

Pick a small, fixed set of "canary" queries that represent RIDE's actual discovery-api-driven access patterns — at minimum one full-table scan, one filtered/partition-pruned scan, one join, and one aggregation, against tables of realistic production size (not empty QA fixtures). Pull the shapes from Trino's own query history if it's retained, rather than guessing.

  • Run the canary set on a schedule (e.g. hourly) starting in Phase 0, continuing unchanged through Phase 3–5, so there is a continuous time series rather than a single before/after snapshot — a step change is much easier to attribute to a specific phase's config change that way.
  • Pull elapsed_time, queued_time, and peak_memory per query from Trino's system.runtime.queries table (or an event-listener plugin, if one is already wired up) rather than timing from the client side, to exclude client/network overhead unrelated to the object store.
  • Tag every recorded run with environment, timestamp, and which object-store engine/endpoint was active at that time — without that tag the time series can't be sliced by phase.
  • If Trino JMX metrics are already scraped into an existing Grafana/Prometheus setup, prefer adding a panel there over standing up new bespoke storage — reuse whatever the team already trusts for other latency baselines.

6.3 Synthetic S3 benchmark script

The canary queries in 6.2 measure the full stack (Trino + network + object store) but can't by themselves say which layer regressed. A small, protocol-level benchmark that talks directly to whichever engine is under test — the same way ExAws and Trino's native-S3 filesystem do — closes that gap and produces numbers that are directly comparable between MinIO and the candidate engine because it's the same client code hitting both.

What it exercises

  • PUT/GET across a size range that spans real usage: small (~4–256 KB, hosted sample metadata), medium (~8 MB, typical ingested partition .gz), and large (~64 MB+, to trigger multipart) objects
  • ListObjectsV2 under a prefix, mirroring ObjectStorageService.extension_available_for_file?/2 and Hive metastore location listing
  • Concurrency sweeps (1 / 4 / 16 simultaneous clients) to approximate simultaneous Forklift writers and parallel Trino worker reads, not just single-threaded latency

What it records

  • Per operation: mean/p50/p95/p99/max latency in ms, sample count, object size, concurrency level, a free-text label (e.g. minio-incluster vs. candidate-external), and a timestamp
  • Appended as JSON Lines so before/after/candidate runs land in one file and diff cleanly without a database

Implemented with boto3 rather than shelling out to the mc CLI already used operationally in this environment (per the production-context notes in Section 3) — boto3 avoids per-invocation process-spawn overhead that would skew latency measurements at the sub-10ms end, while still speaking plain S3 protocol against either engine. mc (or mc support perf, where the candidate engine's distribution supports it) remains a fine quick sanity check using the same debug pods ops already has in place, just not the source of the recorded comparison numbers.

s3_bench.py boto3, stdlib only otherwise 
#!/usr/bin/env python3
"""Synthetic S3 benchmark for MinIO vs. candidate-engine comparison.

Run once per engine under test, with a distinct --label, from the same
network vantage point (e.g. a throwaway pod in the same namespace as the
apps). Results append as JSON Lines to --out for later before/after diffing.

Example:
  python3 s3_bench.py --endpoint http://minio:9000 --bucket bench-scratch \
      --access-key minioadmin --secret-key minioadmin \
      --label minio-incluster --sizes 4KB,256KB,8MB,64MB \
      --concurrency 1,4,16 --iterations 20 --out results.jsonl

  python3 s3_bench.py --endpoint https://candidate.example.internal --bucket bench-scratch \
      --access-key ... --secret-key ... \
      --label candidate-external --sizes 4KB,256KB,8MB,64MB \
      --concurrency 1,4,16 --iterations 20 --out results.jsonl
"""
import argparse
import json
import os
import statistics
import time
import uuid
from concurrent.futures import ThreadPoolExecutor, as_completed

import boto3
from botocore.config import Config

SIZE_UNITS = {"KB": 1024, "MB": 1024 ** 2, "GB": 1024 ** 3}


def parse_size(s):
    s = s.strip().upper()
    for unit, mult in SIZE_UNITS.items():
        if s.endswith(unit):
            return int(float(s[: -len(unit)]) * mult)
    return int(s)


def make_client(endpoint, access_key, secret_key, region):
    return boto3.client(
        "s3",
        endpoint_url=endpoint,
        aws_access_key_id=access_key,
        aws_secret_access_key=secret_key,
        region_name=region,
        # path-style + SigV4 to match every ex_aws/Trino config in this repo
        config=Config(s3={"addressing_style": "path"}, signature_version="s3v4"),
    )


def timed(fn):
    start = time.perf_counter()
    fn()
    return time.perf_counter() - start


def bench_put_get(client, bucket, size, iterations):
    # Real ingestion writes stream via multipart above a threshold (see
    # Pipeline.Writer.S3Writer / ExAws.S3.Upload.stream_file); for sizes
    # above ~8-16MB, swap put_object for client.upload_fileobj(..., Config=
    # boto3.s3.transfer.TransferConfig(multipart_threshold=8*1024*1024))
    # to exercise the same code path this benchmark is standing in for.
    payload = os.urandom(size)
    keys, put_times, get_times = [], [], []
    for _ in range(iterations):
        key = f"bench/{uuid.uuid4()}.bin"
        keys.append(key)
        put_times.append(timed(lambda k=key: client.put_object(Bucket=bucket, Key=k, Body=payload)))
    for key in keys:
        get_times.append(timed(lambda k=key: client.get_object(Bucket=bucket, Key=k)["Body"].read()))
    for key in keys:
        client.delete_object(Bucket=bucket, Key=key)
    return put_times, get_times


def bench_list(client, bucket, prefix, iterations):
    times = []
    paginator = client.get_paginator("list_objects_v2")
    for _ in range(iterations):
        times.append(timed(lambda: list(paginator.paginate(Bucket=bucket, Prefix=prefix))))
    return times


def pctl(values, p):
    if not values:
        return None
    s = sorted(values)
    return s[int(round((p / 100) * (len(s) - 1)))]


def summarize(op, label, size, concurrency, samples_sec):
    ms = [s * 1000 for s in samples_sec]
    return {
        "op": op, "label": label, "size_bytes": size, "concurrency": concurrency,
        "n": len(ms), "mean_ms": statistics.mean(ms) if ms else None,
        "p50_ms": pctl(ms, 50), "p95_ms": pctl(ms, 95), "p99_ms": pctl(ms, 99),
        "max_ms": max(ms) if ms else None, "ts": time.time(),
    }


def run(args):
    client = make_client(args.endpoint, args.access_key, args.secret_key, args.region)
    results = []
    for size_str in args.sizes.split(","):
        size = parse_size(size_str)
        for conc in (int(c) for c in args.concurrency.split(",")):
            per_worker = max(1, args.iterations // conc)
            with ThreadPoolExecutor(max_workers=conc) as pool:
                futures = [pool.submit(bench_put_get, client, args.bucket, size, per_worker)
                           for _ in range(conc)]
                puts, gets = [], []
                for f in as_completed(futures):
                    p, g = f.result()
                    puts += p
                    gets += g
            results.append(summarize("PUT", args.label, size, conc, puts))
            results.append(summarize("GET", args.label, size, conc, gets))
            print(f"[{args.label}] size={size_str} conc={conc} "
                  f"PUT p50={results[-2]['p50_ms']:.1f}ms GET p50={results[-1]['p50_ms']:.1f}ms")
    results.append(summarize("LIST", args.label, 0, 1,
                              bench_list(client, args.bucket, "bench/", args.iterations)))
    with open(args.out, "a") as fh:
        for r in results:
            fh.write(json.dumps(r) + "\n")


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--endpoint", required=True)
    ap.add_argument("--bucket", required=True)
    ap.add_argument("--access-key", required=True)
    ap.add_argument("--secret-key", required=True)
    ap.add_argument("--region", default="local")
    ap.add_argument("--label", required=True, help="e.g. minio-incluster, candidate-external")
    ap.add_argument("--sizes", default="4KB,256KB,8MB,64MB")
    ap.add_argument("--concurrency", default="1,4,16")
    ap.add_argument("--iterations", type=int, default=20)
    ap.add_argument("--out", default="s3_bench_results.jsonl")
    run(ap.parse_args())

Run cadence:

  • Phase 0: once against the current in-cluster MinIO tenant, and once against the candidate engine standalone — this pair is the baseline referenced everywhere else in this plan.
  • Phase 5, per environment: once immediately before cutover (label tagged with the environment) and once after the monitoring window, from the same vantage point, to confirm the live cutover matches the Phase 0 candidate-engine numbers rather than showing a new, network- or load-specific regression.

7. Open decisions (need stakeholder input before Phase 1)

Which engine?

Self-managed MinIO (no Operator, plain Helm/systemd, avoids the OperatorHub removal without a data-model or client-code change) vs. a different engine (Ceph RGW, SeaweedFS, Garage) vs. MinIO AIStor (paid). This choice does not change anything in this repo's code — only endpoint/credentials/region config — but it drives infra work in openshift-deploy and the network-path decision below.

Where does "outside the cluster" mean, physically?

Same on-prem network, reachable by private IP/VPN with no new firewall rules? Or a genuinely separate network requiring new egress rules, mTLS, or a NAT/proxy? This determines whether the connect-timeout failure mode already seen in production (falling back to public s3.us-east-2.amazonaws.com) needs to be root-caused and fixed before cutover, since it would be far more dangerous once "the real endpoint" is off-cluster.

One bucket-pair per environment, or shared?

Recommend keeping the existing per-environment isolation (dev/QA/prod each with their own data-lake and hosted-files buckets) rather than consolidating, to avoid a cross-environment blast radius during cutover.

Credential management

Today's access/secret keys are static (minioadmin in dev; Vault-sourced in prod per reaper-role patterns seen elsewhere in this environment). Confirm whether the new engine should be wired into the same Vault path convention, and whether STS/AssumeRole (already an optional dependency via ex_aws_sts, referenced in forklift's performance.exs) should be adopted more broadly rather than long-lived static keys.

10. Testing & validation plan

Automated

  • Existing integration suites (andi, reaper, discovery_api, forklift, pipeline) run unmodified against the new engine in CI/local docker-compose.
  • e2e suite, which already wires together reaper → forklift → trino → discovery_api against a shared MinIO instance today.

Manual smoke tests, per environment at cutover

  • Andi: upload a sample file via the public-submissions flow (exercises presigned PUT)
  • Andi: download a previously-uploaded sample (exercises presigned GET)
  • Reaper: run a host-type and an "s3"-extract-step ingestion end to end
  • Forklift: confirm a fresh ingestion compacts into its main Trino table
  • Discovery API: download a hosted file end to end through /download
  • Discovery API/Trino: run a representative query and compare latency to the pre-migration baseline
  • Run s3_bench.py (Section 6.3) against the environment with the same --label convention used at Phase 0, and diff against that phase's baseline run before signing off on the environment

Load / soak

  • Ingest at normal production cadence for at least one full day against the new engine in QA before touching prod.
  • Replay a sample of real discovery-api query volume against QA Trino pointed at the new engine to validate the network-path latency assumption from Section 5.
  • Keep the Section 6.2 canary-query schedule running unmodified through the soak window so the continuous time series covers it, not just discrete before/after points.

11. Rollback plan

Per-environment rollback (Phase 5)

Because the old MinIO tenant is kept running (read-only, if supported) through the retention window in Phase 6, rollback for any single environment is: scale the affected pods to 0, revert the env vars/config from Phase 2/3 back to the MinIO endpoint, restart. Any data written to the new engine after cutover but before a rollback decision would need to be re-synced back to MinIO (reverse mc mirror) before resuming against the old endpoint, to avoid data loss for that window.

Point of no return

Once Phase 6 decommissions the old MinIO tenant, rollback is no longer possible without a restore from backup. Do not proceed to Phase 6 until the full retention window has passed with no issues observed in production.
