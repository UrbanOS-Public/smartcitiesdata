Reaper & ANDI: Trusting an Internal CA Certificate

How to make Reaper's real ingestion fetch and ANDI's "test" button trust an internal/private CA (e.g. a state agency's own certificate authority) — not just the public CAs each HTTP library ships with. Written while investigating a mdotatms.state.mi.us ingestion that worked via wget but failed from both ANDI and Reaper, 2026-08-05.

Why this exists

A reaper ingestion against a Michigan DOT ATMS endpoint worked perfectly via wget from the reaper node, but failed both when tested from ANDI's ingestion "test" button and when Reaper ran it for real on schedule. ANDI's UI gave no useful error at all — every failure collapses into a generic "Could not complete request" string (apps/andi/lib/andi/services/url_test.ex:24).

Manually driving Reaper's actual HTTP client (Reaper.Http.Downloader.download/3) from an IEx remote console with the same URL and headers succeeded — clean 200, valid TLS handshake — which ruled out the URL/headers/auth themselves as the problem. That, combined with the "works via wget, not via our Elixir HTTP clients" symptom, pointed at the trust store each client uses to validate the server's certificate chain.

The core insight: three different trust stores

wget, Reaper, and ANDI don't actually share one "the OS trusts this cert or it doesn't" answer — each uses a different certificate bundle by default:

ClientHTTP stackDefault trust bundleReads the OS bundle?
wget system OpenSSL/GnuTLS /etc/ssl/certs/ca-certificates.crt (the OS bundle) yes always
Reaper's real extraction Mint, used directly in Reaper.Http.Downloader.connect/2 the castore hex package's own vendored Mozilla bundle (CAStore.file_path()) no unless explicitly told to
ANDI's "test" button Tesla + Hackney adapter (apps/andi/lib/andi/services/url_test.ex) Hackney's own vendored certifi bundle no unless explicitly told to
Erlang's :ssl application (which both Mint and Hackney sit on top of) does not fall back to the OS trust store. Both libraries depend on their own vendored CA bundle specifically because Erlang won't read /etc/ssl/certs automatically — you have to pass cacertfile or cacerts explicitly. Any CA that's trusted at the OS level (added via update-ca-certificates) is invisible to Reaper and ANDI until they're told where to look.

How the consolidated bundle is built

/etc/ssl/certs/ca-certificates.crt on Debian/Alpine is not one certificate — it's a generated, consolidated bundle. apk add ca-certificates installs the full standard/Mozilla CA set; anything dropped into /usr/local/share/ca-certificates/ and followed by running update-ca-certificates gets merged into that same file, alongside the standard set — it does not replace it.

The root Dockerfile already does exactly this for Amazon RDS's root CA: 

RUN curl -L \
    -o /usr/local/share/ca-certificates/rds-ca-2019-root.crt \
    https://s3.amazonaws.com/rds-downloads/rds-ca-2019-root.pem \
    && update-ca-certificates

Verified empirically against the actual build image while investigating this:

148 certificates already in the bundle

$ podman run --rm smartcitiesdata:build \
    sh -c 'grep -c "BEGIN CERTIFICATE" /etc/ssl/certs/ca-certificates.crt'
148

...and the RDS root CA sits right alongside the 148 standard ones, not in place of them:

subject=C = US, O = Amazon, CN = Amazon Root CA 1
subject=C = US, O = Amazon, CN = Amazon Root CA 2
subject=C = US, L = Seattle, ST = Washington, O = "Amazon Web Services, Inc.",
        OU = Amazon RDS, CN = Amazon RDS Root 2019 CA
Implication: adding an internal CA the same way (via update-ca-certificates) does not narrow trust down to just that one cert. It joins the full standard public CA set plus RDS. Pointing Mint/Hackney at that single consolidated file therefore trusts everything the OS trusts, plus the addition — not a single-cert allowlist.

What changed

FileChange
apps/reaper/lib/reaper/http/downloader.ex connect/2 now passes cacertfile: System.get_env("CA_CERTFILE_PATH") to Mint's transport_opts when the env var is set, falling back to Mint's own CAStore default when it isn't (e.g. local dev without the file).
apps/andi/lib/andi/services/url_test.ex The test-button's Tesla/Hackney HEAD request now passes the same path through as ssl_options: [cacertfile: ...] via Hackney's adapter opts, same fallback behavior.
apps/reaper/Dockerfile Added ENV CA_CERTFILE_PATH /etc/ssl/certs/ca-certificates.crt and COPY --from=builder ${CA_CERTFILE_PATH} ${CA_CERTFILE_PATH} — the same pattern apps/andi/Dockerfile already had for its Postgres TLS config, but reaper's image was missing entirely.
root Dockerfile Added a clearly marked comment showing exactly where/how to add the internal CA cert, right after the existing RDS cert block.

What's still needed

Obtain the actual certificate

The State of Michigan's internal CA certificate (the issuing CA, not the MDOT ATMS server's own leaf/site certificate) still needs to be obtained from state IT. Not done yet — this document exists so the code/Dockerfile side is ready the moment it is.

Add it to the root Dockerfile

A placeholder is already left at the right spot in the root Dockerfile:

# TODO: State of Michigan internal CA cert (for reaper ingestion sources like
# mdotatms.state.mi.us that chain to an internal/private CA). Once the .crt
# file is obtained, add it here the same way as the RDS cert above:
#
#   COPY path/to/state-of-michigan-ca.crt /usr/local/share/ca-certificates/
#   RUN update-ca-certificates

No further code changes needed

Both Reaper.Http.Downloader and Andi.Services.UrlTest already read CA_CERTFILE_PATH and pass it through. Once the cert is added to the Dockerfile and the base image + reaper + andi are rebuilt, it takes effect automatically.

How to verify

After rebuilding, confirm the new cert actually landed in the consolidated bundle:

podman run --rm smartcitiesdata:build sh -c \
  'grep -c "BEGIN CERTIFICATE" /etc/ssl/certs/ca-certificates.crt'
# should be 149, not 148

podman run --rm smartcitiesdata:build sh -c \
  'openssl crl2pkcs7 -nocrl -certfile /etc/ssl/certs/ca-certificates.crt 2>/dev/null \
   | openssl pkcs7 -print_certs -noout 2>/dev/null | grep -i michigan'
# should show the new CA's subject/issuer lines

Then confirm the real ingestion succeeds end to end, e.g. from a reaper remote console:

Reaper.IngestionDiagnostic.run("the-ingestion-id")

Caveats & open questions

  • Must be the issuing CA certificate, not the server's leaf certificate. update-ca-certificates is designed to extend the trust store with CAs, not individual site certs — double-check what state IT actually hands over.
  • This is a build-time (baked into the image) mechanism, not a runtime one. Any future change to the internal cert (renewal, rotation) requires a rebuild and redeploy of the base image plus reaper and andi — there's no ConfigMap/Secret-mounted alternative wired up here. That tradeoff was chosen deliberately (baked-in, matching the existing RDS-cert pattern) rather than a runtime-mounted cert, which would need cluster-side setup.
  • Only covers Reaper's real extraction and ANDI's test button. Other HTTP call sites in the platform (e.g. discovery_api's outbound calls, if any exist) were not audited as part of this change and would need the same CA_CERTFILE_PATH wiring if they ever need to reach an internal endpoint.
  • Not yet proven to be the actual root cause. TLS/certificate verification was the leading hypothesis for why Reaper's real extraction failed while wget succeeded, based on Mint's strict defaults and the vendored-bundle mismatch described above — but this was not confirmed against the real MDOT ATMS certificate chain before this document was written. Confirm with Reaper.IngestionDiagnostic.run/1 (see above) once the cert is in place.
